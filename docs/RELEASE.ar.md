# تجهيز النشر — قائمة مستقبلية، وليس تصريح جاهزية

المشروع الحالي نسخة تطوير 0.1.0+1. يحتوي إدارة أدوية وSQLite وإشعارات محلية محدودة وسجل جرعات. المصدر يستهدف API 36، لكن APK المتاح للبناء التجريبي يستهدف API 35؛ ولم يُختبر تسليم الإشعارات على جهاز Android أو يُنتج AAB إصدار. لا تنشره كتطبيق تذكير جاهز.

## الأدوات والمنصة

في مراجعة 28 أكتوبر 2026، [متطلبات Google Play](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en-sg) تنص على API 36 للتطبيقات الجديدة وتحديثاتها منذ 31 أغسطس 2026. الإعداد الحالي يرث compileSdk/targetSdk من Flutter 3.29.2، ولا نعتبره مطابقاً لمتطلبات النشر. قبل الإصدار: حدّث Flutter stable وAndroid SDK وAGP وGradle وفق التوافق الرسمي، أعد حل الحزم، ثم حدّد targetSdk=36 أو أحدث مطلوب وقتها. راجع أيضاً توافق مكتبات native مع صفحات ذاكرة 16 KB على أجهزة 64-bit.

## الهوية والتوقيع

- أكّد هوية الناشر وملكية applicationId قبل أول رفع. الاسم الحالي app.dawaei.dawaei مبدئي.
- راجع أيقونة launcher الحالية، وأنتج أيقونة متجر وfeature graphic ولقطات حقيقية بالعربية والإنجليزية عند اكتمال الواجهات.
- أنشئ upload keystore خاصاً واحتفظ بنسخة احتياطية آمنة منه. لا تضع كلمة المرور أو keystore في Git.
- فعّل Play App Signing، وأضف signingConfigs.release عبر ملف key.properties محلي متجاهل في Git أو متغيرات CI آمنة. إعداد release الحالي لا يستخدم مفتاح debug ولا يتضمن مفتاح إصدار.
- ارفع versionCode في كل إصدار، وحدّث versionName وAppInfo معاً.

بعد إكمال الإعداد والاختبارات، من جذر المشروع:

```powershell
flutter pub get
flutter analyze
flutter test
flutter build appbundle --release
```

الناتج المتوقع بعد نجاح البناء: build/app/outputs/bundle/release/app-release.aab. إنشاء AAB لا يثبت التوقيع أو توافق السياسات بمفرده. افحص التوقيع وmanifest المدموج وnative libraries، ثم ارفع لمسار اختبار داخلي قبل الإنتاج.

## السياسات والإفصاحات

- رابط سياسة خصوصية عام، فعّال، بلا حجب جغرافي وغير PDF، مع نفس السياسة داخل التطبيق. يجب إضافة هوية الناشر ووسيلة اتصال حقيقية قبل النشر؛ النص التأسيسي الحالي ليس سياسة نشر نهائية.
- أكمل Data Safety حسب سلوك الـAPK وجميع SDKs الفعلية. التخزين على الجهاز فقط ليس إرسال بيانات للمطور، لكن يجب تدقيق plugins والنسخ الاحتياطي والتقارير قبل اختيار إجابات «لا نجمع بيانات».
- أكمل [Health apps declaration](https://support.google.com/googleplay/android-developer/answer/14738291?hl=en) ضمن Medication and Treatment Management حسب الوظائف المنفّذة؛ لا تصف التطبيق كجهاز طبي أو تقدم مزاعم علاجية.
- اشرح أن التذكيرات تنظيمية ولا تقدم نصيحة طبية، وأن missed تعني عدم التأكيد.
- راجع [سياسة exact alarms](https://support.google.com/googleplay/android-developer/answer/16558241?hl=en). لا يستخدم التطبيق `USE_EXACT_ALARM` أو `USE_FULL_SCREEN_INTENT`. يطلب `SCHEDULE_EXACT_ALARM` باختيار المستخدم، ويستخدم جدولة inexact عند عدم السماح بالدقة.
- راجع target API، Health policy، Data Safety والمتطلبات الخاصة بحساب المطور من جديد يوم التقديم؛ الالتزام لا يُضمن بوثيقة ثابتة.

## قبول الإصدار

- نجاح اختبارات مراحل البيانات والتذكيرات والسجل، وتحقيق خطة أجهزة Android الموثّقة.
- تشغيل دون إنترنت، استعادة سليمة بعد تحديث، وعدم فقدان السجل عند تعديل الجدول.
- عدم تكرار الإشعارات، deep links صحيحة بعد cold start، وشفافية نهاية أفق التغطية.
- اختبار منع backup/transfer، إخفاء التفاصيل في lock screen، ومسح البيانات مع إلغاء كل التذكيرات.
- TalkBack، تباين، النص المكبّر، شاشات ضيقة، العربية والإنجليزية، والثيمات.
- لا بيانات صحية في logs/crash reporting، ولا permissions غير ضرورية في manifest النهائي.
- إصدار موقع، اختبار Play pre-launch، استكمال إقرارات الحساب وسياسة الخصوصية، ومراجعة نتائج الاختبار المغلق قبل الإنتاج.
